== Umumiy Ma'lumot

{project-name} - xususiy klinika uchun ishlab chiqilgan full-stack Medical Records Management System.
Tizim shifokorlar, bemorlar, tashxislar, foydalanuvchi accountlari, klinika statistikasi, role-based access control va xavfsiz authentication jarayonlarini bitta web platformada boshqaradi.

Loyiha BTEC Full Stack Development assignment ssenariysi asosida yaratilgan: CareTrack Clinic qog'oz yozuvlar va alohida spreadsheetlardan voz kechib, markazlashgan web-based MRMS tizimiga o'tadi.

=== Asosiy Maqsad

CareTrack Clinic MRMS quyidagi muammolarni hal qiladi:

* bemor yozuvlarini markazlashtirish
* shifokor-bemor bog'lanishini aniq yuritish
* tashxis tarixini klinik record sifatida saqlash
* har bir inson uchun login account yaratish
* Super Admin, Admin, Doctor va Patient rollariga mos ruxsatlarni qo'llash
* klinika faoliyatini dashboard orqali ko'rish
* medical data access va mutationlarni audit log orqali kuzatish

=== Super Admin

Super Admin eng yuqori ruxsat darajasiga ega.

Ruxsatlar:

* full dashboard access
* admins CRUD

* patients CRUD
* diagnoses CRUD

[source,json]

  "message": "This doctor is assigned to one or more patients and cannot be deleted."

=== Admin

Admin Super Admindan pastroq boshqaruv rolidir.

Ruxsatlar:

* dashboard ko'rish
* doctors CRUD
* patients CRUD
* diagnoses CRUD

* `super_admin` account yaratolmaydi

* `super_admin` role assign qilolmaydi
* admin yoki super admin accountlarini boshqara olmaydi
* assigned patientlari bor doctorni o'chira olmaydi

== Security Architecture

=== Authentication

Authentication quyidagicha ishlaydi:

. User email va password bilan login qiladi.
. Backend passwordni bcrypt hash bilan solishtiradi.
. Access token JWT sifatida yaratiladi.
. Access token `httpOnly` cookie ichiga yoziladi.
. Refresh token random secure token sifatida yaratiladi.
. Refresh token hash ko'rinishida `RefreshSession` modelida saqlanadi.
. Frontend API requestlarda `withCredentials: true` ishlatadi.
. Access token tugasa frontend `/api/auth/refresh` endpoint orqali sessionni rotate qiladi.

=== Token Storage

Access token endi `localStorage`da saqlanmaydi.
Bu XSS bo'lsa token o'g'irlanish riskini kamaytiradi.

Cookie options:

* `httpOnly: true`
* `secure: true` productionda
* `sameSite: strict` productionda
* `sameSite: lax` developmentda

=== Session Management

Tizimda quyidagi session flowlar bor:

* `POST /api/auth/login`
* `POST /api/auth/refresh`
* `POST /api/auth/logout`
* `POST /api/auth/logout-all`

`logout-all` userning barcha active refresh sessionlarini revoke qiladi va `tokenVersion` oshiradi.

=== Password Policy

Strong password policy:

* kamida 12 belgi
* kamida bitta uppercase
* kamida bitta lowercase
* kamida bitta number
* kamida bitta special character

Weak passwordlar validator orqali rad etiladi.

=== Account Lockout

Login brute-force hujumlariga qarshi:

* `MAX_LOGIN_ATTEMPTS=5`
* `ACCOUNT_LOCK_TIME=15m`

Noto'g'ri login attemptlar limitdan oshsa account vaqtincha locked bo'ladi.

=== Rate Limiting

Security middleware:

* global API limiter
* auth endpointlar uchun alohida login limiter
* slow down middleware

Bu brute-force va request flooding risklarini kamaytiradi.

=== Security Headers

`helmet` orqali HTTP security headers qo'llanadi.
Productionda Content Security Policy ham yoqiladi.

=== Sanitization

Quyidagilar qo'llanadi:

* `express-mongo-sanitize`
* `hpp`
* custom script-string sanitization
* JSON body limit: `100kb`
* multipart/form-data default reject qilinadi

File upload hozircha yoqilmagan.
Bu ataylab qilingan: upload feature qo'shilganda alohida file type whitelist, size limit, virus scanning va storage policy kerak bo'ladi.

=== Audit Logging

`AuditLog` quyidagi sensitive yo'llarni kuzatadi:

* auth endpoints
* users endpoints
* doctors endpoints
* patients endpoints
* diagnoses endpoints

Audit log quyidagilarni yozadi:

* actor user
* actor role
* action
* resource
* resourceId
* method
* path
* statusCode
* IP
* user-agent
* query metadata

=== Application-level Encryption

`Diagnosis.notes` field application-level AES-256-GCM encryption helper orqali saqlanadi.
Kalit `FIELD_ENCRYPTION_KEY` orqali beriladi.
Kalit bo'lmasa fallback sifatida `JWT_SECRET` ishlatiladi, lekin productionda alohida `FIELD_ENCRYPTION_KEY` berilishi kerak.

=== HTTPS Enforcement

Productionda `ENFORCE_HTTPS=true` bo'lsa HTTP requestlar HTTPSga redirect qilinadi.
Production env validation `FRONTEND_URL` ichida `localhost` yoki `http://` bo'lsa serverni ishga tushirmaydi.

== Troubleshooting

=== Login Ishlamayapti

Tekshiring:

* seed qayta ishlatilganmi
* demo parollarda `!` borligini unutmang
* backend server ishlayaptimi
* frontend `VITE_API_URL` to'g'rimi
* browser cookies block qilinmaganmi
* CORS `FRONTEND_URL` frontend origin bilan mosmi

=== `Not authorized, token missing`

Sabablar:

* cookie browserda saqlanmagan
* frontend `withCredentials: true` ishlamayapti
* backend CORS `credentials: true` bilan ishlamayapti
* frontend va backend originlari mos emas

=== Productionda Server Ishga Tushmayapti

`validateEnv.js` production safety tekshiruvlari sabab bo'lishi mumkin.

Tekshiring:

* `JWT_SECRET` 32+ character
* `MONGO_URI` bor
* `FRONTEND_URL` HTTPS origin
* `FRONTEND_URL` localhost emas

=== Doctor Delete Bo'lmayapti

Agar doctor patientlarga assigned bo'lsa, tizim delete qilishga ruxsat bermaydi.

Response:

[source,json]
----
{
  "message": "This doctor is assigned to one or more patients and cannot be deleted."
}
----

Avval patientlarni boshqa doctorga o'tkazing yoki patientlarni delete qiling.

=== Password Reset Email Ketmayapti

Developmentda SMTP bo'lmasa reset token JSON response va console logda ko'rinadi.
Productionda quyidagilar kerak:

* `SMTP_HOST`
* `SMTP_PORT`
* `SMTP_USER`
* `SMTP_PASS`
* `MAIL_FROM`
